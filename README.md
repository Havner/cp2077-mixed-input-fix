# MixedInputFix

A RED4ext plugin that fixes the Cyberpunk 2077 (2.11+) freeze and input-hint
flicker with **mixed controls** - any setup that sends both gamepad and
mouse/keyboard input at the same time:

- Steam Controller / Steam Deck with touchpad or gyro mapped to mouse
- DualShock/DualSense or other pads with gyro-to-mouse
- gamepad in one hand, mouse in the other
- analog keyboards (e.g. Wooting) mapping movement keys to a virtual stick
- any similar remapper setup (Steam Input, JoyShockMapper, reWASD, ...)

In vanilla, every such input flips the game's "current input device" back and
forth, the on-screen button hints flicker between keyboard and gamepad
variants, and after 20-60 minutes of play the game hard-freezes and is then
killed by its own watchdog. CDPR has declined to fix it ("unsupported
configuration"). Full story and investigation: [bug.md](bug.md), also
published as
[a post on r/cyberpunkgame](https://www.reddit.com/r/cyberpunkgame/comments/1obho7g/the_mixed_inputs_bugfreezecrash_cdpr_refuses_to/)
with further discussion and other players' reports.

With the plugin, the UI is pinned to the device of your choice; the flicker
and the freeze are gone. The raw input layer is untouched - mouse, cursor and
all inputs keep working exactly as before.

## Install

1. Install [RED4ext](https://github.com/WopsS/RED4ext).
2. Copy `MixedInputFix.dll` (and optionally `MixedInputFix.ini`) to
   `<game>/red4ext/plugins/MixedInputFix/`.

Built and tested on game version 2.31 (GOG). Expected to work on Steam and
Epic builds of the same patch: all code addresses resolve through the game's
address library at runtime. On an incompatible future patch the plugin fails
loudly at startup (RED4ext error naming the missing hash) rather than
misbehaving silently.

## Config

`MixedInputFix.ini` next to the DLL. Missing file or entry = defaults.

- `enabled` (default `true`) - `false` makes the plugin attach nothing; the
  game runs fully vanilla. The kill switch if a game patch misbehaves.
- `mode` (default `controller`) - which device the UI is pinned to:
  - `controller`: UI locks to the gamepad after its first input. For
    gamepad-primary setups (Steam Controller/Deck, gyro aim). The game is
    100% vanilla until a gamepad is used.
  - `kbm`: UI locks to keyboard/mouse from boot. For KBM-primary setups with
    auxiliary analog inputs (e.g. movement/driving on a stick).
- `verbose` (default `false`) - per-event logging for debugging.

## What "pinned" means (it goes beyond visuals)

Once engaged, *every* device-dependent choice the game makes follows the
pinned device - not just how the UI looks:

- **UI visuals**: button-hint icons, contextual HUD hint layouts (KBM and
  gamepad variants differ - some actions are one key on keyboard but a
  button combo on a pad), shard/codex popup layouts, gamepad-specific hint
  bars (world map etc.).
- **UI behavior**: the CrystalCoat vehicle color editor keeps one navigation
  paradigm instead of flickering between its KBM and gamepad variants; the
  phone HUD and the settings menu's DualSense detection follow the pinned
  device too.
- **Gameplay branches that check the input device**: the game scripts also
  consult "last used device" for behavior, and those checks follow the pin
  as well - e.g. crouch/dodge handling (on gamepad, dodge and crouch share
  a button, so whether a dodge leaves you crouched follows different rules
  than on keyboard) and body-carry interactions.

This is deliberate - the paradigm follows the device you actually think in.
Worth knowing: in vanilla mixed input these checks were effectively random -
each one read whichever device happened to send the last input event, so
behavior like dodge-exit crouching flip-flopped mid-play. The plugin makes
all of them deterministic and mutually consistent with the chosen mode.

### Keyboard menu shortcuts (controller mode)

One consequence is worth calling out. While the UI is pinned to the gamepad,
the keyboard menu keys stop responding to a tap: holding `M` still opens the
map, but `J`/`P`/`K`/`I` do nothing at all. The game gates those five actions
on the last-used device and picks the *hold* variant for a gamepad, because
the pad's Start button opens the player menu on tap and the map on hold - and
of the five, only the map declares a hold event, so the rest are left with no
working path. Not a plugin bug; the derivation is in
[RE-notes.md](RE-notes.md).

The optional `MixedInputMenuKeys.reds` (own download, own version) restores
them without altering the Start button. Copy it to
`<game>/r6/scripts/MixedInputMenuKeys/`; it needs
[redscript](https://github.com/jac3km4/redscript), and it is inert unless
something pins the device, so it is safe to leave installed.

## Verify

Check `<game>/red4ext/logs/mixedinputfix-*.log`:

- startup: `MixedInputFix 1.0.0 active (mode:controller writer:on
  scriptKBM:on scriptPad:on scriptPS5:on latch:on+on)`
- first gamepad input (controller mode): `gamepad detected (device 5): UI
  device is now locked to gamepad` (5 = XInput; other pad types 2..9)
- on exit: `session summary: suppressed=... scriptKBM=... fallbackRestores=...`
- `[fallback:...]` warnings should be rare (session init at most); frequent
  ones mean a game patch added a new writer path - please report them.

## Build from source

```
powershell -ExecutionPolicy Bypass -File build.ps1
```

Requires MSVC (`vcvars64.bat` path at the top of `build.ps1`) and the
header-only RED4ext.SDK submodule (`git submodule update --init`). Output and
all intermediates land in `build/`.

Note: the submodule deliberately tracks the
[psiberx fork of RED4ext.SDK](https://github.com/psiberx/RED4ext.SDK) (the
variant used by Codeware) rather than upstream WopsS - it is what this plugin
was developed and tested against; upstream has minor macro differences.

## How it works

Short version - three cooperating layers, all bound via RED4ext
address-library hashes (full reverse-engineering record with the derivations,
evidence and failed approaches: [RE-notes.md](RE-notes.md)):

1. **Writer suppression** (the core fix). The ink UI resolves all button-hint
   icons from a single device field (`[[InkSystem]+0x210]+0x1E0`,
   `input::EInputDevice`). That field has exactly one steady-state writer, an
   InkSystem method that polls the current device and, on change, rewrites
   the field and broadcasts device-change notifications - the flicker, and
   the per-event UI churn whose accumulation causes the freeze (reproduced
   and measured, see RE-notes). The plugin hooks the writer, derives the
   would-be value the same way the writer does, and skips it entirely when
   it would switch away from the pinned device: no write, no broadcasts, no
   churn.
2. **Script-side stickiness.** Game scripts read the device through the
   natives `PlayerLastUsedKBM/Pad/PS5Pad` (a separate mechanism - it drives
   the contextual HUD hint *layouts*, popup layouts etc.). All script calls
   funnel through their registered native handlers; the plugin hooks those
   and forces the answers to match the pinned device.
3. **Fallback latch** (watchdog). Independent hooks observe the field and
   restore the pinned value if anything outside the suppressed writer ever
   changes it (e.g. session-init code), logging a warning - so hook coverage
   is verifiable from any user's log. If the writer hook ever failed to
   attach on some game build, this latch alone still provides the fix at
   v0.6 level (proven in testing).

| hook | addr-lib hash | purpose |
|------|---------------|---------|
| device writer (InkSystem method) | 3719303744 | core fix: suppress switches off the pinned device |
| `PlayerLastUsedKBM` native handler | 1037639234 | script-side device answer |
| `PlayerLastUsedPad` native handler | 1291656829 | script-side device answer |
| `PlayerLastUsedPS5Pad` native handler | 2647269205 | script-side device answer (DualSense detection) |
| hint icon refresh (`inkInputDisplayController`) | 4042789608 | fallback latch + coverage watchdog |
| `inkSystem::ProcessInputEvents` | 673454961 | fallback latch, once per UI input pump |
| InkSystem instance pointer | 2635337807 | (data, not a hook) |

The hashes survive game patches; the four struct offsets involved
(`0x210`/`0x1E0`/`0x300`/vtbl `0x218`) are per-patch and may need
re-derivation - the procedure is documented in RE-notes.md ("Porting to a
new game patch") and the `tools/` directory contains the analysis scripts
that make it a ~10 minute job.

## Writer diagnostic (opt-in, for porting)

Create an empty file `MixedInputFix.diag` next to the installed DLL and start
the game: the plugin arms a hardware write-watchpoint on the device field and
logs every writer's instruction address as `exe+0x...` (the RIP is the
instruction *after* the write; the plugin's own writes are filtered;
auto-disarms after ~400 events). One short mixed-input session is enough;
delete the marker afterwards. The offsets feed directly into
`tools/dumpfunc.py`. This is how the writer was originally found.

## Version history

- 0.1-0.5 - failed approaches (kept honest in RE-notes.md so nobody retries
  them: device-activation hook fires on the wrong layer; pointer-mode
  suppression breaks the cursor).
- 0.6 - read-side latch on the hint device field. First working version:
  flicker gone, no freeze in long sessions. Regression: gamepad hint bars on
  some screens (world map) could hide and never re-show.
- 0.7 - added the opt-in hardware-watchpoint diagnostic; located the field's
  single writer.
- 0.8 - writer-level suppression: switches off the pinned device are skipped
  inside the game's own writer - no hide broadcasts, no churn. Fixed the
  world-map regression at the root.
- 0.9 / 0.9.1 - script-side stickiness via the `PlayerLastUsed*` native
  handlers: fixed the contextual HUD hint widget flickering between its KBM
  and gamepad layout variants; all script device checks made consistent.
- 1.0.0 - release: `MixedInputFix.ini` (`enabled`, `mode`, `verbose`) with
  the new `kbm` mode (mirror-image stickiness for KBM-primary players),
  quiet-by-default logging with a session summary on exit, fail-soft hook
  attachment. Validated: vanilla freeze reproduced in ~25 min of intensive
  mixed input; with the fix, multi-hour sessions run clean at well past the
  vanilla freeze threshold with zero fallback events.
